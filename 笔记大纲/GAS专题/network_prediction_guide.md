## 1. 服务器权威与延迟问题

### 1.1 服务器权威原则

在多人游戏中，服务器应拥有对游戏状态**重大变更的权威**：

- 如果客户端可以改变关键因素，会留下作弊者可利用的漏洞
- 如果客户端必须等待服务器确认其请求变更的有效性，则在"客户端执行操作"与"看到结果"之间会产生明显延迟

### 1.2 为什么需要预测

```
客户端执行操作 → [网络延迟] → 服务器确认 → [网络延迟] → 客户端看到结果
```

- 延迟会带来明显的不跟手感
- **快节奏的多人游戏必须使用预测**

<a id="s2"></a>
## 2. 预测的基本工作流程

### 2.1 核心思想

**预测 = 客户端先行变更，服务器后确认。**

客户端先执行：

- 移动角色
- 打开门
- 射击武器

然后向服务器报告该变更。

### 2.2 服务器验证

服务器收到信息后，会确保该变更**有效**：

- 角色没有撞墙或瞬间跨越地图
- 没有打开无法触及的门
- 没有使用未拥有的武器射击

### 2.3 无效变更的处理

如果变更无效，服务器将**撤销这些变更**，以保证可玩性。

```
客户端立即执行变更 → 同时报告服务器
                            ↓
服务器验证 → 有效 → 确认（客户端继续）
         → 无效 → 撤销变更（回滚）
```

## 3. GAS 的预测范围

### 3.1 GAS 的目标：自动预测

游戏能力系统（GAS）的目的是实现游戏逻辑、能力与预测，让能力**自动**正常运作。开发者不希望能力中充满分支条件（如"权威执行 X，否则执行预测版 X"），他们希望预测机制更自动化。

### 3.2 并非所有内容都需要预测

| 不需要预测 | 需要预测 |
|-----------|---------|
| 脚步声 | 生命值变化 |
|  | 法力消耗 |
|  | 造成伤害 |

服务器应默认对这些变更有最终决定权。

### 3.3 GAS 自动预测的内容

| 自动预测 | 说明 |
|---------|------|
| 能力激活 | ✅ |
| 触发事件 | ✅ |
| 游戏效果（GE）应用 | ✅ 包括属性修改，**不包括执行计算（尚未实现）** |
| 游戏标签修改 | ✅ |
| 游戏提示（Gameplay Cue） | ✅ 无论来自预测能力还是独立触发 |

### 3.4 GAS 不预测的内容

| 不预测 | 原因 |
|--------|------|
| 游戏效果移除 | 尚未解决的技术挑战 |
| 周期性效果 | 尚未解决的技术挑战 |

另外，过场动画和移动也被预测，但那是得益于虚幻引擎的 **UCharacterMovementComponent** 移动系统，不属于 GAS 自身实现。

## 4. 预测密钥 Prediction Key

### 4.1 预测密钥是什么

GAS 预测的核心概念围绕**预测密钥（FPredictionKey）**：

- 预测密钥只是一个**唯一标识符**
- 密钥存储在客户端的中央位置
- 当客户端执行预测性操作时，会将预测密钥发送到服务器
- 客户端把自己的预测操作和副作用与该密钥关联

### 4.2 密钥的完整流转

```
客户端                                  服务器
  │                                      │
  │ 执行预测性操作                        │
  │ 生成预测密钥                          │
  │ 操作/副作用 ↔ 密钥关联                │
  │──────────────── 密钥 ───────────────►│
  │                                      │ 接受或拒绝该密钥
  │                                      │ 服务器端副作用 ↔ 密钥关联
  │◄──────── 密钥接受/拒绝响应 ───────────│
  │ 按响应执行确认/回滚                   │
```

### 4.3 "复制到服务器"的含义

注意：此前我们说"复制仅从服务器到客户端"，那指的是**复制变量**（用 `UPROPERTY(Replicated)` 标记的变量）。

而预测密钥是从客户端发往服务器，这里用"复制"一词只是为了方便表述，实际机制是 RPC / 网络序列化。

### 4.4 密钥只会返回给原客户端

- 当服务器返回预测密钥时，只会返回给**最初发送密钥的那个客户端**
- 其他客户端收到的是**无效密钥或 ID 为零的密钥**
- 这一行为由 `FPredictionKey` 的**网络序列化函数**保证

## 5. 能力激活：第一类预测操作

### 5.1 第一类预测操作

GAS 中的**游戏能力（Gameplay Ability）是第一类预测操作**：

- 每当客户端预测性激活能力时，会明确告知服务器
- 并会获得服务器的明确响应（成功 / 失败）

### 5.2 预测窗口

每当客户端预测性激活能力时，存在一个预测操作可能发生的时间窗口——**预测窗口（Prediction Window）**。

在此窗口开启期间，客户端可以执行改变游戏状态的重要操作（例如消耗属性资源等），**无需请求服务器许可**。

<a id="s6"></a>
## 6. TryActivateAbility 完整流程

能力系统组件（ASC）提供了客户端与服务器之间激活能力的通信函数，其中最核心的就是 **TryActivateAbility**。

### 6.1 流程分解

```
客户端调用 TryActivateAbility
    │
    ├─ ① 生成新的预测密钥
    │     （即 GetActivationPredictionKey 获取的密钥）
    │
    ├─ ② 调用服务器 RPC（ServerTryActivateAbility）
    │
    ├─ ③ 客户端不等服务器确认，继续执行
    │     使用生成的预测密钥调用 ActivateAbility
    │     密钥被标记在该能力激活的信息中
    │
    ├─ ④ 客户端执行操作并产生副作用
    │     所有副作用都与该预测密钥关联
    │
    ▼
服务器收到 RPC
    │
    ├─ 判断能力激活是否有效
    │
    ├─ 失败 → 调用 ClientActivateAbilityFailed
    │
    └─ 成功 → 调用 ClientActivateAbilitySucceeded
              │
              ▼
客户端收到响应
    │
    ├─ 失败：终止该能力 + 撤销与预测密钥相关的所有副作用
    │
    └─ 成功：副作用有效，无需撤销
```

### 6.2 ReplicatedPredictionKey

- ASC 中有一个名为 **ReplicatedPredictionKey** 的成员变量
- 被设置为生成的预测密钥
- 设置完成后会复制（同步）到客户端
- 客户端随后可以做出响应（如撤销副作用）
- 该预测密钥有自己的**复制通知（OnRep）**，在密钥复制时触发

<a id="s7"></a>
## 7. 副作用与 Gameplay Effect

### 7.1 什么是副作用

**游戏效果（Gameplay Effect）就是典型的副作用**：

- GE 不是显式预测操作（不像能力激活那样）
- 若能力有有效预测密钥，GE 仅在客户端应用
- 若 GE 被预测，则它执行的所有操作也都是预测的：
  - 属性修改
  - 游戏标签修改
  - 激活时的游戏提示（Gameplay Cue）

### 7.2 GE 的预测与去重

```
服务器存储预测密钥
激活的 GE 获取相同密钥
激活的 GE 在客户端复制
    │
    ▼
客户端接收复制数据
    │
    ├─ 检查：是否已有使用相同密钥的相同效果？
    │
    ├─ 匹配 → 本地已执行效果逻辑，无需重复执行
    │          （避免重复应用，自定义预测中常见问题）
    │
    └─ 不匹配 → 正常应用
```

### 7.3 临时双份效果与清理

- 本地存储所有激活 GE 的容器中，会**暂时存在两个相同效果**（至少暂时如此）
- 此时 ASC 的 ReplicatedPredictionKey 正在向下复制到客户端
- 当它最终到达时，所有预测效果均可移除

## 8. 与 CS:GO 网络预测对比

### 8.1 核心对比

| 维度 | **GAS 预测** | **CS:GO 网络同步** |
|-----|--------------|-------------------|
| 引擎 | Unreal Engine（GAS 插件） | Source Engine（Valve 自研） |
| 预测对象 | 能力激活、GE 应用、属性/标签修改 | 玩家移动、射击、命中判定 |
| 核心机制 | 预测密钥（FPredictionKey） | 延迟补偿（Lag Compensation） |
| 回滚范围 | 单个能力及其副作用 | 全游戏状态（玩家位置、命中判定） |
| 服务器权威 | 是 | 是，但客户端也参与命中判定 |
| 实现复杂度 | GAS 封装好，较易用 | 底层优化，复杂 |

### 8.2 一句话总结

> **GAS 预测：用预测密钥自动管理"能力 + 副作用"的确认与回滚。**
>
> **CS:GO 延迟补偿：回滚全游戏状态到客户端看到的那一刻，解决射击判定。**

## 9. 总结

### 9.1 核心流程

1. **客户端预测**：客户端先执行操作，不等服务器
2. **密钥关联**：预测操作和副作用都与预测密钥关联
3. **服务器确认**：服务器接受或拒绝密钥
4. **失败回滚**：密钥被拒绝 → 终止能力 + 撤销全部副作用
5. **去重机制**：服务器返回的 GE 与本地预测 GE 通过密钥匹配，避免重复应用

### 9.2 核心原则

1. 服务器始终拥有最终决定权
2. 快节奏多人游戏必须使用预测
3. GAS 自动预测：能力激活、触发事件、GE 应用、标签修改、游戏提示
4. GAS 不预测：GE 移除、周期性效果（尚未解决的技术挑战）
5. 并非所有内容都需要预测（脚步声不需要，生命值/法力/伤害需要）

### 9.3 深入参考

如需更多信息，可参考引擎源码 **GameplayPrediction.h**，其中的注释详细解释了本视频讨论的大部分内容，包括：

- 游戏属性的预测处理
- 实现预测系统时遇到的高级挑战

### 10.1 基础概念

#### 10.1.1 三个独立的时间线

在多人游戏中，存在三个独立的时间流：

| 时间线 | 说明 | 特点 |
|--------|------|------|
| **现实时间** | 绝对客观时间 | 无法直接观测 |
| **服务器时间** | 服务器处理逻辑的时间 | 权威但延迟 |
| **客户端时间** | 玩家屏幕上显示的时间 | 最延迟但最直观 |

#### 10.1.2 网络延迟的构成

```
客户端 A 发送数据 → [上传延迟] → 服务器处理 → [下载延迟] → 客户端 B 收到

总延迟 = 上传延迟 + 服务器处理时间 + 下载延迟
       ≈ RTT/2 (Round Trip Time / 2)
```

#### 10.1.3 为什么需要预测

在多人游戏中，数据在网络上传输需要时间（延迟）。如果没有预测：

```
客户端执行操作 → [网络延迟 100ms] → 服务器接收 → [网络延迟 100ms] → 客户端收到确认 → 生效
```

- 延迟 100ms 或更长时间并不罕见
- 玩家执行操作后要等很久才能看到效果，体验极差

<a id="s12"></a>
### 10.2 无预测的工作流程

#### 10.2.1 流程图

```
客户端请求更改 → [网络延迟] → 服务器接收 → 判断有效性 → [网络延迟] → 客户端收到确认 → 更改生效
```

#### 10.2.2 射击场景示例

```
t=0      客户端 A 瞄准 B 头部，按下鼠标
         ↓ 发送射击请求（50ms 上传延迟）

t=50     服务器收到请求
         B 已经移动到新的位置
         射线检测：未命中 ❌

         ↓ 发送结果（50ms 下载延迟）

t=100    客户端 A 收到"未命中"
         A 的屏幕上：明明打中了，服务器说没打中！
         体验极差！
```

#### 10.2.3 问题分析

| 问题 | 原因 |
|------|------|
| 操作响应慢 | 必须等待服务器确认 |
| 手感不跟手 | 按键到看到反馈有延迟 |
| 命中判定不公平 | 客户端看到的位置和服务器不一致 |

### 10.3 客户端预测（Client Prediction）

#### 10.3.1 核心思想

客户端**立即执行**操作，不等服务器确认，同时发送请求给服务器。

```
客户端立即更改属性（无需等待） → 同时发送请求给服务器
                                     ↓
服务器判断有效性 → 有效则确认 → 无效则通知客户端回滚
```

#### 10.3.2 有预测的工作流程

```
t=0      客户端 A 按下 W 向前走
         客户端立即移动角色（预测）
         同时发送移动指令给服务器

t=50     服务器收到移动指令
         服务器计算移动，验证合法性

         ↓ 发送确认（50ms）

t=100    客户端 A 收到服务器确认
         对比预测位置 ≈ 服务器位置 → 无事发生 ✓
         对比预测位置 ≠ 服务器位置 → 平滑修正
```

#### 10.3.3 预测的好处

- 客户端**立即**感知到变化，没有延迟
- 服务器仍然保持**权威**（可以拒绝无效操作）
- 预测是多人游戏中创造流畅体验的关键因素

#### 10.3.4 预测的代价

```
如果预测错误：
客户端位置 = (10, 0, 5)  // 预测
服务器位置 = (9, 0, 5)    // 实际

需要平滑插值修正：
(10, 0, 5) → (9.8, 0, 5) → (9.5, 0, 5) → (9, 0, 5)
玩家会看到角色"漂移"回正确位置
```

<a id="s14"></a>
### 10.4 延迟补偿（Lag Compensation）

#### 10.4.1 为什么需要延迟补偿

客户端预测解决了"自己操作"的延迟问题，但没有解决"射击其他玩家"的延迟问题。

```
问题场景：
- A 的屏幕上：B 在位置 X（这是 100ms 前的状态）
- A 瞄准 X 开枪
- 服务器收到时：B 已经走到 X+2
- 服务器判定：未命中！
- A 觉得：明明打中了！
```

#### 10.4.2 延迟补偿的核心思想

**服务器回滚到客户端"看到的那一刻"做判定。**

#### 10.4.3 关键公式

```
A 开枪时的本地时间 = A_t

A 屏幕上显示的服务器时间 = A_t - A的延迟

服务器应该回滚到的时间 = A_t - A的延迟
                      = A屏幕上看到的那一刻
```

#### 10.4.4 延迟补偿的工作流程

```
t=0      B 走到位置 X
         B 发送"我在 X，时间戳 B_t=0"

t=50     服务器收到 B 的移动包
         记录：服务器_t=50，B 在 X

t=100    B 走到位置 X+2δ
         B 发送"我在 X+2δ，时间戳 B_t=100"

         A 的屏幕上：显示 B 在 X（服务器_t=50 的状态）
         A 瞄准 X 开枪
         A 发送"我开枪，时间戳 A_t=100"

t=150    服务器收到 A 的开枪包

         【延迟补偿计算】
         A 的包延迟 = 50ms
         A_t=100 对应的服务器时间 = 100 - 50 = 50
         所以 A 瞄准的是服务器_t=50 的状态！

         查服务器_t=50 的历史：
         - B 在 X（来自 B_t=0 的包）

         服务器回滚 B 到 X
         射线检测：命中！✓

         同时：收到 B_t=100 的包
         更新 B 的当前位置到 X+2δ

         通知所有客户端：B 被击中
```

#### 10.4.5 延迟补偿的本质

```
A 的屏幕上显示的是"过去"（50ms前）
A 瞄准的是"过去"的位置
服务器回滚到"过去"做判定
→ 两者对齐！✓

如果服务器回滚到"现在"（t=100）：
A 瞄准的是 X（过去）
B 在服务器_t=100 时可能在 X+δ
→ 两者不对齐！✗ A 会觉得没打中
```

#### 10.4.6 延迟补偿的代价

```
B 客户端视角：
- B_t=100: B 觉得自己在 X+2δ（掩体后面）
- B 的屏幕上：自己已经安全了
- 但服务器判定：B 在 X 被击中

结果：B 觉得自己已经躲到掩体后了，还是被爆头！
→ "我都躲到墙后面了还被爆头！"
```

**总有人要吃亏，CS:GO 选择让开枪者爽，被打的吃亏。**

### 10.5 完整时间线分析

#### 10.5.1 三个独立时钟

```
【B客户端时钟】        【服务器时钟】        【A客户端时钟】
     t=0                  t=0                  t=0
      │                    │                    │
      ▼                    ▼                    ▼
   B走到X               服务器启动            A启动
      │                    │                    │
      ▼                    ▼                    ▼
   发送"我在X"            等待...               等待...
   时间戳: B_t=0                              
      │                    │                    │
      └──────50ms────────►│                    │
                           │                    │
                        收到B的包              │
                        B在X(B_t=0)            │
                           │                    │
                           ▼                    │
                        记录历史:               │
                        服务器_t=50时           │
                        B在X(B_t=0)           │
                           │                    │
                           │                    │
      ◄─────50ms─────────┘                    │
   B_t=100                                    │
   B走到X+2δ                                  │
      │                                       │
      ▼                                       │
   发送"我在X+2δ"                              │
   时间戳: B_t=100                             │
      │                                       │
      └──────50ms────────────────────────────►│
                                              │
                                           A_t=100
                                              │
                                           A看到B在X
                                           （服务器_t=50的状态）
                                              │
                                           A瞄准X开枪
                                           发送"我开枪"
                                           时间戳: A_t=100
                                              │
                                              └────50ms──►
                                                                  │
                                                               服务器_t=150
                                                                  │
                                                               收到A的开枪
                                                               "A在A_t=100开枪"
                                                                  │
                                                               同时：
                                                               刚收到B的第二个包
                                                               B在X+2δ(B_t=100)
                                                                  │
                                                               【延迟补偿】

                                                                  │

                                                                  │

                                                               判定：命中！✓
```

#### 10.5.2 关键修正

| 错误理解 | 正确理解 |
|---------|---------|
| 服务器把 A_t=100 对应到服务器_t=100 | 服务器把 A_t=100 对应到服务器_t=50 |
| 查服务器_t=100 时 B 的位置 | 查服务器_t=50 时 B 的位置 |
| 忽略了 A 的屏幕延迟 | 考虑了 A 的屏幕延迟（A看到的就是50ms前的） |

#### 10.5.3 为什么 A_t=100 对应服务器_t=50？

```
A_t=100 时，A 的屏幕上显示的是什么？

不是服务器_t=100 的状态！
而是服务器_t=50 的状态！（因为 A 有 50ms 延迟）

对应关系：
A 的本地时间    A 屏幕上看到的服务器时间
─────────────────────────────────────
A_t=50         服务器还没数据
A_t=100        服务器_t=50
A_t=150        服务器_t=100
A_t=200        服务器_t=150

规律：A 屏幕上显示的服务器时间 = A_t - 50ms
```

### 10.6 为什么 CS:GO 能做到延迟补偿？

**Source Engine 保存玩家历史位置：**

```cpp
class CPlayer {
    // 保存最近 1 秒的位置历史（64 tick = 64 个位置点）
    Vector positionHistory[64];
    float timestampHistory[64];

    void RewindPosition(float targetTime) {
        // 二分查找最接近 targetTime 的历史位置
        int idx = BinarySearch(timestampHistory, targetTime);
        SetPosition(positionHistory[idx]);
    }
};
```

**UE 为什么不内置？**

1. **通用性**：UE 是通用引擎，不是所有游戏都需要射击延迟补偿
2. **性能**：回滚所有玩家位置开销大，UE 选择让开发者按需实现
3. **架构**：GAS 是高层系统，延迟补偿是底层网络层

### 10.8 总结

#### 10.8.1 三种预测方式对比

| 方式 | 适用场景 | 回滚机制 | 实现难度 |
|-----|---------|---------|---------|
| **普通属性同步** | 简单属性变化 | ❌ 无自动回滚 | 低 |
| **GAS Gameplay Prediction** | 技能释放、复杂游戏逻辑 | ✅ 内置自动回滚 | 中 |
| **CS:GO 延迟补偿** | 射击游戏命中判定 | ✅ 全状态回滚 | 高 |

#### 10.8.2 核心原则

1. **客户端预测**：解决"自己操作"的延迟问题
2. **延迟补偿**：解决"射击其他玩家"的延迟问题
3. **服务器权威**：服务器始终有最终裁决权
4. **总有人吃亏**：延迟补偿让开枪者爽，被打的吃亏

#### 10.8.3 一句话记忆

> **"预测"是通用概念：客户端先执行，服务器后确认。**
>
> **GAS 的 Gameplay Prediction 是"高级版"：自动管理预测窗口、自动回滚、属性快照。**
>
> **CS:GO 的延迟补偿是"射击特化版"：回滚全游戏状态到客户端看到的那一刻。**
>
> **CS:GO 是"专用跑车"，UE/GAS 是"通用 SUV"。跑赛道 CS:GO 更快，但 UE 什么路都能走。**
