## 一、问题背景

俯视角 RPG 常见两种鼠标移动方式：

- **点击并立即松开**：角色自动寻找路径并移动到目标位置。
- **按住鼠标不放**：角色持续朝鼠标当前所在方向移动。

UE 的 Top Down 模板已经实现了这两种行为。在单机模式下，它们看起来都能正常工作；进入多人模式后却会出现明显差异：

| 操作 | 监听服务器上的主机角色 | 远程客户端角色 |
|---|---|---|
| 按住鼠标持续移动 | 正常 | 正常 |
| 点击后松开，自动寻路 | 正常 | 基本无效 |

这不是导航网格失效，而是两种移动方式走了不同的底层通道：

```text
长按移动
    └── AddMovementInput
        └── CharacterMovementComponent 的网络预测与复制

短按寻路
    └── SimpleMoveToLocation
        └── AI 导航移动逻辑，不是本地玩家的预测移动输入
```

> 核心问题：如何既利用导航系统生成可绕开障碍物的路径，又通过支持客户端预测的角色移动组件实际驱动玩家角色？

<a id="section-4"></a>
## 二、点击移动的两种输入行为

### 2.1 为什么要区分短按和长按

系统通过一个累计时间 `FollowTime` 判断玩家意图：

```text
鼠标按下
    ↓
每帧累加 FollowTime
    ↓
鼠标松开
    ├── FollowTime <= ShortPressThreshold：短按，自动寻路
    └── FollowTime >  ShortPressThreshold：长按，停止跟随光标
```

这种设计让同一个鼠标按键同时支持：

- 快速点击目的地后自动行走。
- 按住后实时改变移动方向。

### 2.2 三种输入阶段

增强输入通常把一次按键拆成三个阶段：

| 输入阶段 | 典型 TriggerEvent | 用途 |
|---|---|---|
| 开始按下 | `Started` | 清理旧移动状态或停止当前寻路 |
| 持续按住 | `Triggered` | 累计时间、更新鼠标位置并逐帧移动 |
| 松开按键 | `Completed` / `Canceled` | 判断短按或长按，并决定是否生成自动路径 |

只有把“按下多久”和“松开时做什么”分开处理，才能准确区分两种移动意图。

<a id="section-7"></a>
## 三、UE 俯视角模板的实现

### 3.1 按下：停止原有移动

在开始按下时，模板会停止当前移动，防止角色继续沿上一条自动路径行走。

```text
新的鼠标输入开始
    ↓
StopMovement
    ↓
旧的自动导航结束
```

### 3.2 持续：朝光标方向添加移动输入

按住鼠标时，每帧执行以下逻辑：

1. 累加 `FollowTime`。
2. 获取鼠标光标下的 HitResult。
3. 缓存命中的世界坐标 `CachedDestination`。
4. 用目标位置减去角色位置，得到移动向量。
5. 对向量调用 `GetSafeNormal()` 得到单位方向。
6. 调用 `AddMovementInput(Direction)`。

核心计算：

```text
Direction = Normalize(CachedDestination - PawnLocation)
```

伪代码：

```cpp
FollowTime += DeltaSeconds;

if (GetHitResultUnderCursor(HitResult))
{
    CachedDestination = HitResult.Location;
}

if (APawn* ControlledPawn = GetPawn())
{
    const FVector Direction =
        (CachedDestination - ControlledPawn->GetActorLocation()).GetSafeNormal();

    ControlledPawn->AddMovementInput(Direction);
}
```

### 3.3 松开：短按时调用 SimpleMoveToLocation

松开鼠标后，模板检查 `FollowTime`：

```cpp
if (FollowTime <= ShortPressThreshold)
{
    UAIBlueprintHelperLibrary::SimpleMoveToLocation(
        this,
        CachedDestination);
}

FollowTime = 0.f;
```

短按时还可以在目标点生成 Niagara 特效，为玩家显示点击反馈。

### 3.4 模板行为总结

```text
按住：每帧 AddMovementInput
    优点：响应即时、支持客户端预测和多人同步
    缺点：只会朝当前目标直线移动，不主动绕开障碍物

短按：SimpleMoveToLocation
    优点：使用导航系统，能够绕开障碍物
    缺点：不适合作为远程客户端玩家角色的本地移动入口
```

<a id="section-12"></a>
## 四、为什么长按移动支持多人游戏

### 4.1 AddMovementInput 的职责

`AddMovementInput` 不会直接瞬移角色，而是把本帧的移动意图交给 Pawn/Character 的移动组件。

对于 `ACharacter`，主要由 `UCharacterMovementComponent` 消费这个输入，并完成：

- 移动速度与加速度计算。
- 碰撞检测和地面处理。
- 客户端本地预测。
- 向服务器发送移动数据。
- 服务器校验与权威模拟。
- 预测错误后的平滑修正。
- 向其他客户端复制角色位置。

### 4.2 拥有客户端的移动流程

```text
客户端按住鼠标
    ↓
本地每帧 AddMovementInput
    ↓
CharacterMovement 立即预测移动
    ├── 玩家本地马上看到角色移动
    └── 将移动数据发送给服务器
            ↓
        服务器重放并校验移动
            ↓
        位置正确：确认
        位置有误：发送修正
            ↓
        客户端平滑校正
```

### 4.3 为什么不需要手写“移动 RPC”

`CharacterMovementComponent` 已经提供成熟的网络移动协议。正常情况下，玩家移动应尽量通过它的输入与预测系统完成，而不是每帧自定义 RPC 发送坐标。

手写坐标 RPC 容易产生：

- 网络流量过大。
- 延迟导致明显卡顿。
- 缺少预测与回滚。
- 客户端可直接伪造位置。
- 与碰撞、速度、根运动等系统冲突。

> `AddMovementInput` 的关键价值不仅是“让角色移动”，而是进入了 CharacterMovement 的完整多人移动链路。

<a id="section-16"></a>
## 五、为什么短按自动寻路在客户端失效

### 5.1 SimpleMoveToLocation 的定位

`UAIBlueprintHelperLibrary::SimpleMoveToLocation` 使用导航系统为 Controller 控制的 Pawn 发起移动请求。它特别适合：

- 由服务器控制的 AI。
- 单机游戏中的简单导航移动。
- 不需要复杂自定义控制的 Pawn。

它不是为“拥有客户端在本地发起、并自动进入 CharacterMovement 预测协议的玩家点击移动”设计的。

### 5.2 服务器 AI 为什么可以使用

服务器拥有 AI 的控制权：

```text
服务器 AIController
    ↓ SimpleMoveToLocation
导航系统生成路径
    ↓
服务器驱动 AI Pawn 移动
    ↓
角色移动结果复制到各客户端
```

整个决策和移动都发生在服务器权威端，所以不存在“客户端的本地导航请求如何同步给服务器”的问题。

### 5.3 玩家客户端为什么不能直接依赖它

远程玩家的点击发生在拥有客户端。如果只在本地调用 `SimpleMoveToLocation`：

- 服务器没有收到等价的玩家移动输入。
- 调用没有自动转换成 CharacterMovement 的预测移动序列。
- 客户端无法像服务器 AIController 那样权威驱动导航。
- 本地结果可能很快被服务器状态覆盖或直接不产生有效移动。

因此会出现字幕中的现象：

- 监听服务器上的主机角色短按有效，因为主机同时是服务器。
- 远程客户端短按无效，因为 AI 简单移动没有合适的客户端预测/同步通道。
- 客户端长按有效，因为它持续调用 `AddMovementInput`。

### 5.4 不应得出的错误结论

问题不是：

- NavMesh 不能用于多人游戏。
- 客户端永远不能计算导航路径。
- 玩家角色不能自动寻路。

真正的问题是：

> 不能把面向 AI/服务器控制的 `SimpleMoveToLocation`，直接当成远程客户端玩家角色的完整网络移动方案。

导航系统仍然可以负责“路径怎么走”，只是最终的玩家移动需要通过合适的网络移动通道执行。

## 六、导航网格与路径点

### 6.1 NavMesh 的作用

`NavMeshBoundsVolume` 定义可导航区域。引擎根据场景碰撞生成导航网格，路径查询会在可行走区域中寻找起点到终点的路线。

在编辑器中按 `P` 可以显示导航网格。

```text
角色起点
    ↓
导航系统查询可行走区域
    ↓
绕开墙、柱子和不可行走区域
    ↓
目标点
```

### 6.2 路径由多个点组成

当起点和终点之间存在障碍物时，导航查询返回一组路径点：

```text
P0（角色位置）
  ↓
P1（障碍物一侧）
  ↓
P2（绕过障碍物）
  ↓
P3（目标位置）
```

角色可以逐段朝下一个路径点调用 `AddMovementInput`：

```text
Direction = Normalize(NextPathPoint - CurrentLocation)
AddMovementInput(Direction)
```

### 6.3 直接追逐路径点的问题

路径点组成的是折线。角色到达节点后，目标方向会突然改变：

```text
P0 ───── P1
          │
          │
          P2 ───── P3
```

可能产生：

- 角色朝向突然跳变。
- 拐角运动生硬。
- 高速移动时越过节点并来回修正。
- 角色在狭窄拐角附近抖动。

因此仅有路径点还不等于拥有良好的移动表现。

## 七、多人点击寻路的目标方案

### 7.1 将“规划”和“执行”拆开

更合适的思路是：

| 阶段 | 负责系统 | 输出 |
|---|---|---|
| 路径规划 | Navigation System | 从角色到目标的可行路径点 |
| 路径平滑 | Spline | 连续、平滑的前进方向 |
| 移动执行 | CharacterMovement | 预测、复制、碰撞与服务器校验 |

```text
导航系统回答：应该沿哪条路线走？
样条曲线回答：当前应该朝哪个平滑方向走？
CharacterMovement 回答：这一帧角色如何合法移动并同步？
```

### 7.2 基本算法

短按鼠标后：

1. 获取光标命中的目标位置。
2. 查询角色位置到目标位置的导航路径。
3. 读取路径中的所有节点。
4. 用路径点构建样条曲线。
5. 开启自动行走状态。
6. 每帧从样条获取角色附近的前进方向。
7. 调用 `AddMovementInput(Direction)`。
8. 接近终点后关闭自动行走。

伪代码：

```cpp
void BeginAutoRun(const FVector& Destination)
{
    NavigationPath = FindPathToLocationSynchronously(
        GetWorld(),
        GetPawn()->GetActorLocation(),
        Destination);

    BuildSplineFromPathPoints(NavigationPath->PathPoints);
    bAutoRunning = true;
}

void UpdateAutoRun()
{
    if (!bAutoRunning) return;

    const FVector PawnLocation = GetPawn()->GetActorLocation();
    const FVector Direction = GetSplineDirectionNear(PawnLocation);
    GetPawn()->AddMovementInput(Direction);

    if (FVector::Dist(PawnLocation, CachedDestination) <= AcceptanceRadius)
    {
        bAutoRunning = false;
    }
}
```

> 这段代码表达的是架构思路，不是可直接复制的最终实现。具体 API 和样条查询方式需要结合项目代码确定。

### 7.3 为什么仍然能够多人同步

导航查询只负责产生方向，真正推动角色的仍是每帧调用的 `AddMovementInput`：

```text
点击目标
    ↓
本地生成路径和样条
    ↓
本地每帧计算 Direction
    ↓
AddMovementInput(Direction)
    ↓
CharacterMovement 网络预测与服务器校验
```

这样同时保留：

- 导航系统的绕障能力。
- CharacterMovement 的本地响应速度。
- 多人移动的预测、复制和服务器修正。

## 八、为什么使用样条曲线

### 8.1 样条提供连续方向

样条曲线把离散路径点拟合成平滑曲线。曲线上任意位置都有切线方向：

```text
路径点折线： P0 ─── P1
                    └──── P2

平滑样条：   P0 ～～～～ P1 ～～～～ P2
```

角色移动时可以读取样条切线作为方向：

```text
Direction = SplineDirectionAtClosestPoint(PawnLocation)
```

方向会随着角色沿曲线前进而连续变化，避免到达节点时突然转向。

### 8.2 样条的职责边界

样条并不负责：

- 计算哪里可以行走。
- 驱动角色网络移动。
- 处理服务器权威性。
- 自动避开动态障碍物。

它只是在导航路径基础上提供更平滑的几何方向。

### 8.3 平滑曲线可能切入障碍物

这是实现时非常重要的风险。导航路径的折线位于可行走区域内，但平滑样条可能在拐角处“切弯”，离开 NavMesh 或穿进障碍物。

```text
导航折线安全绕角： ─────┐
                         │

过度平滑的曲线：   ────╮│  ← 可能切入墙角
```

因此不能无条件提高曲线平滑度。可以采用：

- 减小样条切线长度。
- 在尖锐拐角保留线性插值。
- 对样条采样点重新投射到 NavMesh。
- 检查样条分段是否穿过不可行走区域。
- 给障碍物保留与角色胶囊半径匹配的安全距离。

> 导航路径保证“折线可走”，并不自动保证“拟合后的任意曲线也可走”。

## 九、完整数据流

### 9.1 长按跟随光标

```text
鼠标 Started
    ↓
停止旧的自动移动
    ↓
鼠标 Triggered（每帧）
    ├── FollowTime += DeltaSeconds
    ├── 获取光标 HitResult
    ├── 更新 CachedDestination
    ├── Direction = Normalize(Destination - PawnLocation)
    └── AddMovementInput(Direction)
            ↓
        CharacterMovement 预测与复制
```

### 9.2 短按自动寻路

```text
鼠标 Started
    ↓
鼠标短时间 Triggered
    ↓
鼠标 Completed
    ↓ FollowTime <= ShortPressThreshold
查询 NavigationPath
    ↓
PathPoints → Spline
    ↓
bAutoRunning = true
    ↓ PlayerController Tick / 输入 Held 更新
获取样条前进方向
    ↓
AddMovementInput(Direction)
    ↓
到达 AcceptanceRadius
    ↓
bAutoRunning = false
```

### 9.3 障碍物存在时

```text
角色位置 A ── 障碍物 ── 目标 D
        ↓ 导航查询
路径点 A → B → C → D
        ↓ 构建安全的平滑样条
样条 A ～～ B ～～ C ～～ D
        ↓ 每帧读取切线
AddMovementInput(当前方向)
```

## 十、服务器权威与客户端预测

### 10.1 本地计算路径不等于本地决定结果

为了获得即时响应，拥有客户端可以先计算一条路径并开始调用 `AddMovementInput`。但最终位置仍由服务器权威确认。

```text
客户端：计算路径、立即预测移动
服务器：验证 CharacterMovement 上报的移动
其他客户端：接收服务器复制的位置
```

只要实际位移通过 CharacterMovement 执行，就能利用其现有的预测和纠错机制。

### 10.2 客户端与服务器导航数据必须一致

如果客户端和服务器的 NavMesh、动态障碍或目标投射结果不同，可能发生：

- 客户端认为路径可行，服务器持续阻挡。
- 客户端预测方向与服务器环境不一致。
- 角色频繁被服务器拉回。

因此多人项目需要确保：

- 关卡静态导航数据在各端一致。
- 关键动态障碍由服务器权威管理。
- 目标点最好投射到可导航区域。
- 对高风险移动，可以由服务器验证目标或重新计算路径。

### 10.3 可选的权威方案

根据项目的安全性和复杂度，可以选择不同方案：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 客户端计算路径并逐帧输入 | 响应快、实现直接 | 客户端与服务器导航不一致时会修正 |
| 客户端提交目标，服务器计算路径 | 权威性高 | 需要把路径或方向结果反馈给客户端，首帧响应较慢 |
| 客户端预测路径，服务器独立验证/重算 | 手感和权威兼顾 | 实现复杂，需要处理路径差异 |

对于课程中的基础点击移动，重点是避免客户端直接依赖 `SimpleMoveToLocation`，改为把路径转换成持续的 `AddMovementInput`。

## 十一、实现时的关键注意事项

### 11.1 到达判定不能要求完全重合

角色很难精确到达一个浮点坐标，应使用接受半径：

```cpp
if (DistanceToDestination <= AcceptanceRadius)
{
    bAutoRunning = false;
}
```

接受半径应考虑角色胶囊大小、制动距离和移动速度。

### 11.2 避免越过路径点后反复折返

如果只判断“是否非常接近下一个点”，高速角色可能一帧越过节点，随后回头追逐，产生抖动。

更稳定的方法包括：

- 使用样条最近点和距离推进。
- 根据与路径平面的点积判断是否越过节点。
- 使用足够合理的节点接受半径。

### 11.3 新输入应中断旧路径

以下情况通常需要停止自动行走：

- 玩家再次点击。
- 玩家开始按住鼠标手动跟随。
- 玩家按下 WASD 等直接移动输入。
- 技能使角色眩晕、定身或死亡。
- 目标点或导航路径失效。

### 11.4 动态障碍需要重新规划

初始路径只代表生成时可行。门关闭、角色阻挡或场景变化后，旧路径可能失效。

可根据项目需要：

- 定期检查当前路径是否仍有效。
- 长时间没有前进时重新寻路。
- 目标移动较远时重新生成路径。
- 使用局部避障系统处理其他移动角色。

### 11.5 将导航和能力输入分开

虽然点击移动可能复用 `InputTag.LMB`，但“鼠标左键是移动还是释放技能”通常取决于光标下对象和当前状态：

```text
鼠标左键 Held
    ├── 光标指向敌人：技能输入/攻击
    └── 光标指向地面：移动或自动寻路
```

PlayerController 适合负责输入意图与地面寻路；GameplayAbility 负责技能的激活和执行。不要把完整导航逻辑塞进 Ability 中，除非移动本身就是一个受 GAS 生命周期控制的能力。

### 11.6 GAS 与移动系统的关系

点击寻路本身不是 GAS 专属功能，但会和 GAS 状态标签产生交互。例如：

```text
State.Dead       → 禁止移动
State.Stunned    → 暂停或取消自动寻路
State.Rooted     → 允许转向但不能 AddMovementInput
Abilities.Attack → 攻击开始时停止自动行走
```

GAS 负责表达角色是否允许移动，CharacterMovement 负责真正移动角色，导航系统负责计算路径。

<a id="section-48"></a>
## 十二、总结

### 核心结论

1. UE Top Down 模板的长按移动使用 `AddMovementInput`，因此能进入 CharacterMovement 的多人预测与复制流程。
2. 短按自动行走使用 `SimpleMoveToLocation`，它适合服务器控制的 AI 或单机简单移动，不能直接作为远程客户端玩家的完整点击移动方案。
3. NavMesh 仍可用于多人玩家寻路，关键是把导航结果转换成每帧的移动方向。
4. 路径点可以绕开障碍物，但直接逐点追逐会产生生硬转向。
5. 使用样条可以获得连续方向，再通过 `AddMovementInput` 驱动角色，实现平滑且支持网络预测的自动行走。
6. 样条平滑可能切入障碍物，必须结合 NavMesh 投射、曲线采样或保守切线进行安全校验。
7. 客户端负责即时输入反馈，服务器仍负责最终位置和移动合法性的权威判断。

### 一句话总结

> 多人点击寻路的核心不是让 `SimpleMoveToLocation` 在客户端强行工作，而是让导航系统只负责生成路线，用样条提供平滑方向，最终持续调用 `AddMovementInput`，把实际移动交回 CharacterMovement 的预测、复制与服务器校验体系。
