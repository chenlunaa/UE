## 一、本阶段解决了什么问题

此前敌人已经具备属性、血条、受击和死亡等能力，但它仍然是一个被动目标：不会主动寻找玩家，也不会根据距离决定靠近或攻击。

第 15 章前半为敌人补上 AI 的第一条完整数据链：

```text
服务器生成并占有敌人
  -> AAuraEnemy::PossessedBy
  -> 获得 AAuraAIController
  -> 使用行为树资产初始化 Blackboard
  -> 启动 BehaviorTree
  -> 自定义 Service 周期性搜索最近目标
  -> 写入 TargetToFollow 与 DistanceToTarget
  -> Decorator 根据黑板数据选择分支
  -> Move To 读取目标并驱动寻路
  -> 服务器移动结果复制到客户端
```

这次提交不只是“让敌人跟着玩家走”，而是建立了可继续扩展的 AI 架构。以后加入攻击、巡逻、逃跑、施法和控制状态时，可以围绕同一个黑板和行为树继续组合，而不必把大量状态判断硬编码进敌人的 `Tick`。

<a id="section-2"></a>
## 二、敌人 AI 的整体架构

本阶段涉及四个主要对象：

| 对象 | 主要职责 |
|---|---|
| `AAuraEnemy` | 敌人 Pawn/Character，本身承载移动、属性、受击状态以及行为树资产引用 |
| `AAuraAIController` | 在服务器上占有敌人，持有 Blackboard 与 BehaviorTree 组件并协调 AI 执行 |
| Blackboard | 保存 AI 运行时共享数据，例如当前目标、目标距离和是否正在受击 |
| BehaviorTree | 读取黑板数据，按照 Selector、Sequence、Decorator、Task 等节点组织决策流程 |

还新增了一个自定义服务：

| 类 | 作用 |
|---|---|
| `UBTService_FindNearestPlayer` | 按服务间隔搜索最近的合法目标，并把目标对象及距离写入黑板 |

这里最重要的理解是：**行为树负责决策结构，黑板负责运行时数据，AIController 负责拥有并启动它们，Enemy 负责真正执行角色行为。**

<a id="section-3"></a>
## 三、AIController、Blackboard 与 BehaviorTree 的职责

### 3.1 为什么不把逻辑全部写进 Enemy Tick

如果所有 AI 都直接写进 `Tick`，代码很快会变成：

```text
每帧查找玩家
  -> 判断是否受击
  -> 判断距离
  -> 判断职业
  -> 决定移动还是攻击
  -> 处理攻击冷却
  -> 处理目标死亡和重新选敌
```

这种结构把感知、状态、决策和动作混在一个函数中，很难可视化，也难以给不同敌人复用不同策略。行为树把它们拆成可组合节点，并允许不同敌人蓝图选择不同的 BehaviorTree 资产。

### 3.2 三者的分工

```text
AAuraAIController
  |-- BlackboardComponent：保存本次运行的数据
  `-- BehaviorTreeComponent：执行行为树

BehaviorTree Asset
  |-- Service：周期性更新感知数据
  |-- Decorator：判断分支能否进入，并监听条件变化
  |-- Composite：Selector / Sequence 组织流程
  `-- Task：执行 Move To、攻击等实际动作
```

BehaviorTree 资产不是数据仓库。目标对象和距离会在运行过程中不断变化，应存入每个 AI 自己的 Blackboard，而不是写入共享资产。

<a id="section-4"></a>
## 四、创建 AuraAIController 并接入 AIModule

### 4.1 模块依赖

使用 UE 的 AIController、Blackboard 和 BehaviorTree API 前，需要在 `Aura.Build.cs` 中加入：

```cpp
"AIModule"
```

这解决的是链接与模块可见性问题；只包含头文件而没有声明模块依赖，项目可能在编译或链接阶段失败。

### 4.2 创建组件

```cpp
AAuraAIController::AAuraAIController()
{
    Blackboard = CreateDefaultSubobject<UBlackboardComponent>(
        "BlackboardComponent");
    check(Blackboard)

    BehaviorTreeComponent = CreateDefaultSubobject<UBehaviorTreeComponent>(
        "BehaviorTreeComponent");
    check(BehaviorTreeComponent)
}
```

两个组件都作为默认子对象创建：

- Blackboard 保存本 AIController 的运行时键值；
- BehaviorTreeComponent 负责执行行为树；
- `check` 用于尽早暴露组件创建失败的问题，开发构建中比让空指针继续传播更容易定位。

敌人蓝图还需要把 AI Controller Class 设置为 `AAuraAIController` 的蓝图子类，并配置 Auto Possess AI，才能让关卡中放置或运行时生成的敌人得到正确 Controller。

<a id="section-5"></a>
## 五、在 PossessedBy 中启动 AI

### 5.1 为什么选择 PossessedBy

`BeginPlay` 时角色虽然已经存在，但不能把“已经获得正确 AIController”当成所有场景下都可靠的前提。`PossessedBy` 在 Controller 正式占有 Pawn 时调用，是接收 `NewController` 并初始化控制逻辑的合适入口。

```cpp
void AAuraEnemy::PossessedBy(AController* NewController)
{
    Super::PossessedBy(NewController);

    if (!HasAuthority()) return;

    AuraAIController = Cast<AAuraAIController>(NewController);

    AuraAIController->GetBlackboardComponent()
        ->InitializeBlackboard(*BehaviorTree->BlackboardAsset);

    AuraAIController->RunBehaviorTree(BehaviorTree);

    AuraAIController->GetBlackboardComponent()
        ->SetValueAsBool(FName("HitReacting"), false);

    AuraAIController->GetBlackboardComponent()
        ->SetValueAsBool(
            FName("RangedAttacker"),
            CharacterClass != ECharacterClass::Warrior);
}
```

### 5.2 初始化顺序

顺序不能随意颠倒：

1. 确认在服务器执行；
2. 把 `NewController` 转成项目自定义 Controller；
3. 使用行为树对应的 `BlackboardAsset` 初始化黑板；
4. 启动行为树；
5. 写入敌人的初始状态和职业分类。

### 5.3 为什么只在服务器运行

AI 决策会改变敌人位置、攻击目标和战斗结果，这些属于权威游戏状态，应由服务器决定。客户端不需要各自运行一套可能产生分歧的行为树，只需接收服务器复制的角色移动和必要状态。

```text
服务器：搜索目标 -> 决策 -> 寻路/移动 -> 攻击
客户端：接收复制位置与状态 -> 播放表现
```

## 六、行为树节点的基本语义

### 6.1 Root

行为树的固定入口。它本身不负责游戏逻辑，而是连接整棵树的顶层节点。

### 6.2 Selector（选择器）

从左到右尝试子节点，直到有一个子节点成功。适合表达“优先做 A，否则做 B，再否则做 C”。

```text
Selector
  |-- 能远程攻击？ -> 远程分支
  |-- 能近战攻击？ -> 近战分支
  `-- 否则 -> 靠近目标
```

### 6.3 Sequence（序列）

从左到右执行子节点，只要有一个失败，整个 Sequence 就失败；全部成功才算成功。适合表达“满足若干前提后，连续完成一组动作”。

### 6.4 Task（任务）

真正执行一个动作，例如 `Move To`、等待或以后要实现的攻击任务。

### 6.5 Decorator（装饰器）

挂在节点或分支上，用黑板条件决定该分支是否允许执行。它相当于行为树中的门禁条件。

### 6.6 Service（服务）

挂在某个分支上，在该分支活跃期间按设定间隔周期执行。搜索最近玩家不要求每帧运行，用 Service 可以降低无意义的频繁查询。

<a id="section-7"></a>
## 七、黑板键与 FBlackboardKeySelector

本阶段使用四个核心黑板键：

| 黑板键 | 类型 | 写入者 | 消费者 |
|---|---|---|---|
| `TargetToFollow` | Object | `BTService_FindNearestPlayer` | Decorator、`Move To`、未来攻击任务 |
| `DistanceToTarget` | Float | `BTService_FindNearestPlayer` | 距离 Decorator，用于选择移动或攻击 |
| `HitReacting` | Bool | `AAuraEnemy::HitReactTagChange` | Decorator，用于阻止或中止行动 |
| `RangedAttacker` | Bool | `AAuraEnemy::PossessedBy` | Decorator，用于区分远程与近战分支 |

自定义服务没有把键名直接写死在代码中，而是声明：

```cpp
UPROPERTY(BlueprintReadOnly, EditAnywhere)
FBlackboardKeySelector TargetToFollowSelector;

UPROPERTY(BlueprintReadOnly, EditAnywhere)
FBlackboardKeySelector DistanceToTargetSelector;
```

`FBlackboardKeySelector` 的作用是让 C++ 节点暴露一个“选择哪个黑板键”的属性。把服务放进行为树后，可以在编辑器中把它们分别绑定到实际的 Object 键和 Float 键。

这样做比在服务中固定写 `FName("TargetToFollow")` 更容易复用：同一个 Service 类可以在另一棵树中绑定不同键名。不过 Enemy 当前对 `HitReacting`、`RangedAttacker` 的写入仍使用硬编码字符串，二者要注意区分。

## 八、FindNearestPlayer 服务的实现

### 8.1 获取执行该树的 Pawn

```cpp
AAIController* AIOwner = OwnerComp.GetAIOwner();
APawn* OwningPawn = AIOwner->GetPawn();
```

Service 先从行为树组件取得 AIController，再取得它正在控制的 Pawn。对于敌人，这个 Pawn 就是 `AAuraEnemy`。

### 8.2 通过 Tag 决定要搜索的阵营

```cpp
const FName TargetTag =
    OwningPawn->ActorHasTag(FName("Player"))
    ? FName("Enemy")
    : FName("Player");
```

这段逻辑不是简单写死“永远搜索 Player”，而是：

- 当前 Pawn 带有 `Player` Tag，就搜索 `Enemy`；
- 否则搜索 `Player`。

因此该服务未来也可以被玩家阵营的 AI 复用。这里的 Tag 是 Actor Tag，而不是 GAS 的 `FGameplayTag`，二者不是同一个系统。

### 8.3 收集候选目标

```cpp
TArray<AActor*> ActorsWithTag;
UGameplayStatics::GetAllActorsWithTag(
    OwningPawn, TargetTag, ActorsWithTag);
```

当前课程场景规模较小，按 Tag 获取所有候选 Actor 足以完成目标搜索。它的代价会随候选数量增长，因此大型场景更适合感知系统、空间查询或维护阵营成员集合。

### 8.4 寻找最近者

```cpp
float ClosestDistance = TNumericLimits<float>::Max();
AActor* ClosestActor = nullptr;

for (auto Actor : ActorsWithTag)
{
    if (IsValid(Actor) && IsValid(OwningPawn))
    {
        const float Distance = OwningPawn->GetDistanceTo(Actor);
        if (Distance < ClosestDistance)
        {
            ClosestDistance = Distance;
            ClosestActor = Actor;
        }
    }
}
```

`TNumericLimits<float>::Max()` 是一个初始哨兵值，表示“当前还没有任何真实距离”。第一个有效 Actor 的距离一定小于它，因此会成为第一个候选最近目标。之后每找到更小的距离，就同时更新距离和 Actor。

该算法对本次候选数组进行一次遍历，时间复杂度为 `O(n)`，额外空间为 `O(1)`（不计前面收集候选 Actor 的数组）。

### 8.5 写回 Blackboard

```cpp
UBTFunctionLibrary::SetBlackboardValueAsObject(
    this, TargetToFollowSelector, ClosestActor);

UBTFunctionLibrary::SetBlackboardValueAsFloat(
    this, DistanceToTargetSelector, ClosestDistance);
```

Service 只负责“感知并发布数据”，不直接控制移动。写入黑板后，Decorator 和 Task 会消费这些值，从而降低搜索逻辑和行为逻辑之间的耦合。

<a id="section-9"></a>
## 九、从搜索目标到 Move To 的数据流

```text
BTService_FindNearestPlayer 周期触发
  |
  |-- GetAllActorsWithTag(Player)
  |-- 遍历并比较 GetDistanceTo
  v
Blackboard
  |-- TargetToFollow = 最近 Actor
  `-- DistanceToTarget = 对应距离
          |
          |-- Decorator：目标是否存在？
          |-- Decorator：距离属于哪个区间？
          v
        Move To
          `-- Blackboard Key = TargetToFollow
```

`Move To` 读取的是 Object 类型黑板键。目标移动后，寻路任务可以持续追踪目标；服务则按周期重新评估“最近目标是否已经换人”。课程中 Move To 的 Acceptance Radius 示例约为 50，表示进入目标附近一定范围即可认为任务完成，不要求角色中心完全重合。

## 十、敌人转向的平滑处理

敌人构造函数新增：

```cpp
bUseControllerRotationPitch = false;
bUseControllerRotationRoll = false;
bUseControllerRotationYaw = false;

GetCharacterMovement()->bUseControllerDesiredRotation = true;
```

这里容易混淆两种旋转方式：

- `bUseControllerRotationYaw = true`：Character 的朝向直接跟随 Controller Yaw，转向可能显得生硬；
- `bUseControllerDesiredRotation = true`：由 CharacterMovement 朝 Controller 期望方向平滑插值，并受 Rotation Rate 控制。

课程蓝图中的 Rotation Rate 示例大约为 400。最终效果是敌人在改变寻路方向时逐渐转身，而不是瞬间“掰头”。

## 十一、EffectActor 对敌人的过滤

AI 能主动移动后，敌人也会碰到场景里的药水、魔法水晶或伤害区域。因此 `AAuraEffectActor` 新增两个配置：

```cpp
bool bDestroyOnEffectApplication = false;
bool bApplyEffectToEnemy = false;
```

### 11.1 是否允许影响敌人

在 `ApplyEffectToTarget`、`OnOverlap` 和 `OnEndOverlap` 中都加入：

```cpp
const bool bIsEnemy = TargetActor->ActorHasTag(FName("Enemy"));
if (bIsEnemy && !bApplyEffectToEnemy) return;
```

因此不同 EffectActor 可以表达不同规则：

- 生命/法力拾取物：默认不被敌人消耗；
- 火焰区域或陷阱：勾选 `bApplyEffectToEnemy` 后也能作用于敌人。

### 11.2 应用后是否销毁

```cpp
if (bDestroyOnEffectApplication && !bIsInfinite)
{
    Destroy();
}
```

只对非 Infinite Effect 自动销毁，是因为无限效果常常需要 EffectActor 保留 `ActiveGameplayEffectHandle`，等离开重叠范围时再移除效果。若应用后立刻销毁，后续移除流程可能没有对象负责执行。

配置文件还加入了属性重定向，把旧名称 `bDestroyOnEffectRemoval` 迁移为 `bDestroyOnEffectApplication`，避免已有蓝图资产因 C++ 属性改名丢失引用。

## 十二、HitReacting 与行为树动态中断

敌人受击时已经会获得 HitReact GameplayTag。本次把这个 GAS 状态同步给黑板：

```cpp
void AAuraEnemy::HitReactTagChange(
    const FGameplayTag CallbackTag,
    int32 NewCount)
{
    bHitReacting = NewCount > 0;

    GetCharacterMovement()->MaxWalkSpeed =
        bHitReacting ? 0 : BaseWalkSpeed;

    AuraAIController->GetBlackboardComponent()
        ->SetValueAsBool(FName("HitReacting"), bHitReacting);
}
```

这段逻辑同时影响两个层次：

1. CharacterMovement：受击时速度变为 0，结束后恢复基础速度；
2. BehaviorTree：黑板 `HitReacting` 改变，Decorator 可以禁止当前行动。

如果 Decorator 的 `Observer Aborts` 设置为 `Self`，当 `HitReacting` 从 false 变成 true 时，正在执行的当前分支会被中止，而不是等待 Move To 或其他 Task 自己结束。

```text
GameplayTag 数量变化
  -> HitReactTagChange
  -> HitReacting = true
  -> MaxWalkSpeed = 0
  -> Blackboard.HitReacting = true
  -> Decorator 重新判断
  -> Abort Self
  -> 当前移动/攻击分支立即停止
```

这体现了 GAS 状态和 AI 决策的连接方式：GameplayTag 是权威战斗状态，Blackboard 是行为树可观察的决策数据。

## 十三、近战、远程与移动分支框架

15.7 搭建的是初始框架，主要分成三条分支：

```text
Selector
  |-- 远程攻击 Sequence
  |     |-- RangedAttacker == true
  |     |-- 目标存在
  |     `-- 距离满足远程攻击条件
  |
  |-- 近战攻击 Sequence
  |     |-- RangedAttacker == false
  |     |-- 目标存在
  |     `-- 距离满足近战攻击条件
  |
  `-- 靠近目标 Sequence
        |-- 目标存在
        |-- 未处于 HitReacting
        `-- Move To(TargetToFollow)
```

`RangedAttacker` 的初始判断是：

```cpp
CharacterClass != ECharacterClass::Warrior
```

即 Warrior 走近战逻辑，其他职业暂时归为远程攻击者。字幕中的测试参数示例包括：

- 近战/通用攻击距离约 500；
- 远程攻击距离示例约 600；
- 接近目标的最大感知距离约 4000；
- Move To 接受半径约 50。

这些数值目前用于搭建和观察行为树，最终应按敌人职业、武器范围、胶囊体大小和战斗节奏数据化配置。

需要特别注明：**截至 15.7，攻击分支只是结构与条件占位，并没有完成真正的攻击 Task 或技能激活。** 当前已经闭环的是“发现目标并移动过去”。

## 十五、源码审查与当前边界

### 15.1 PossessedBy 需要空指针保护

当前代码默认以下对象一定有效：

- `NewController` 能成功转换为 `AAuraAIController`；
- Enemy 已配置 `BehaviorTree`；
- BehaviorTree 已绑定 `BlackboardAsset`。

如果蓝图漏配其中任意一项，后续解引用可能崩溃。后续可加入：

```cpp
if (!IsValid(AuraAIController) ||
    !IsValid(BehaviorTree) ||
    !IsValid(BehaviorTree->BlackboardAsset))
{
    return;
}
```

也可以配合 `ensureMsgf` 输出具体资产配置错误。

### 15.2 HitReactTagChange 的调用时机

当前回调直接使用 `AuraAIController`。如果 GameplayTag 回调在占有完成前触发，或敌人进入了没有自定义 AIController 的测试环境，存在空指针风险。写黑板前应确认 Controller 和 Blackboard 有效。

### 15.3 没有候选目标时的距离值

如果没有找到目标，`ClosestActor` 为 `nullptr`，但距离仍是 `TNumericLimits<float>::Max()`。Object 键清空是合理的，Float 键写入最大值虽然能让距离条件失败，却不够直观。后续可以明确清除键，或约定一个可读的无目标距离值。

### 15.4 搜索成本

`GetAllActorsWithTag` 每次 Service Tick 都要扫描并构造候选数组，小型课程场景可以接受。敌人和玩家数量增加后，可考虑：

- UE AI Perception；
- Sphere Overlap / 空间查询；
- GameState 或子系统维护阵营成员列表；
- 降低 Service 执行频率并加入随机偏移，避免大量 AI 同帧查询。

### 15.5 调试输出残留

当前搜索服务仍用 `GEngine->AddOnScreenDebugMessage` 打印遍历到的 Actor。它适合验证服务是否工作，完成调试后应删除，或用可控日志类别和调试开关替代。

### 15.6 黑板键名的维护

Service 使用 `FBlackboardKeySelector`，但 Enemy 仍直接写 `FName("HitReacting")` 和 `FName("RangedAttacker")`。字符串拼写不会得到编译器检查，改名也难以全局追踪。后续可以集中定义键名常量，减少蓝图和 C++ 不一致的风险。

### 15.7 EffectActor 过滤可以集中

敌人过滤在 `ApplyEffectToTarget`、`OnOverlap`、`OnEndOverlap` 重复出现，且访问 `TargetActor->ActorHasTag` 前没有统一的有效性判断。后续可以封装：

```cpp
bool AAuraEffectActor::CanApplyToTarget(AActor* TargetActor) const;
```

让三条入口共享空指针检查和阵营规则。

## 十六、知识点总结

### 16.1 核心职责速查

| 概念 | 本阶段应记住的作用 |
|---|---|
| AIController | 在服务器上占有 Pawn，拥有并启动 AI 系统 |
| Blackboard | 保存单个 AI 实例的动态共享数据 |
| BehaviorTree | 根据黑板条件组织决策与任务执行 |
| Service | 周期更新感知数据，不必每帧写在 Actor Tick 中 |
| Decorator | 控制分支进入条件，并可在条件变化时中止分支 |
| Selector | 从左到右选择第一个成功的方案 |
| Sequence | 从左到右执行，任何一步失败则整个序列失败 |
| Task | 执行移动、等待、攻击等具体动作 |
| `FBlackboardKeySelector` | 让 C++ 节点在编辑器中绑定实际黑板键 |
| `Observer Aborts: Self` | 条件变化后中止装饰器所在的当前分支 |

### 16.2 本阶段形成的闭环

```text
敌人由服务器 AIController 占有
  -> 初始化黑板并启动行为树
  -> Service 周期搜索最近玩家
  -> Blackboard 保存目标和距离
  -> Decorator 判断目标、距离、职业与受击状态
  -> Move To 驱动敌人靠近目标
  -> HitReacting 可立即打断移动
```

### 16.3 一句话总结

**第 15 章前半把敌人 AI 拆成“Controller 启动、Service 感知、Blackboard 共享数据、BehaviorTree 决策、Task 执行动作”的清晰流水线，并把 GAS 的受击状态接入行为树中断机制；当前完成的是自动选取最近目标与追踪，真正的近战和远程攻击将在后续内容继续实现。**
