## 1. 本次提交完成了什么

本章下半主要新增四部分：

1. 为 FireBolt 创建 Cost GameplayEffect，施法时扣除 Mana；
2. 为 FireBolt 创建 Cooldown GameplayEffect，用 `Cooldown.Fire.FireBolt` 阻止重复激活；
3. 创建 `UWaitCooldownChange` 蓝图异步任务，将 ASC 的冷却事件转换成 `CooldownStart` / `CooldownEnd` 蓝图执行引脚；
4. 在 `WBP_SpellGlobe` 中使用定时器显示倒计时，并在冷却开始/结束时切换技能图标状态。

最终运行链路：

```text
输入触发 FireBolt
  → GAS 检查 Cost 与 Cooldown
  → ActivateAbility
  → CommitAbility
     ├─ 应用 Cost GE：Mana 减少
     └─ 应用 Cooldown GE：ASC 获得 Cooldown.Fire.FireBolt
  → UWaitCooldownChange 监听到冷却 GE
  → CooldownStart(剩余秒数)
  → WBP_SpellGlobe 变暗并启动本地定时器
  → 冷却 GE 到期，CooldownTag 数量变为 0
  → CooldownEnd(0)
  → 技能球恢复可用状态
```

这一设计把“能否释放”交给 GAS，把“如何显示”交给 UI。技能球的倒计时是反馈，不是决定技能是否可释放的权威逻辑。

## 2. Cost：技能消耗系统

### 2.1 创建 Cost GameplayEffect

在 FireBolt 目录中创建：

```text
GE_Cost_FireBolt
```

蓝图配置：

```text
Duration Policy：Instant
Modifiers：
  Attribute：AuraAttributeSet.Mana
  Modifier Op：Add
  Magnitude：-20（或曲线表数值 × -1）
```

Mana 消耗使用负数加法。Instant GE 会立即修改 Mana 的 BaseValue；它不是持续附着在角色身上的状态。

在 `GA_FireBolt` 的 Class Defaults 中，把该 GE 设置为 `Cost Gameplay Effect Class`。

### 2.2 `CommitAbility` 做了什么

在 Ability 激活流程中调用：

```text
Commit Ability
```

它不是单纯扣蓝，而是一次提交两项内容：

```text
CommitAbility
├─ CheckCost / ApplyCost
└─ CheckCooldown / ApplyCooldown
```

如果希望在不同时间提交，可以分别使用 `CommitAbilityCost` 和 `CommitAbilityCooldown`。例如蓄力法术可在开始时先检查资源、成功发射时才扣费；但普通即时技能直接使用 `CommitAbility` 更简单。

### 2.3 为什么资源不足时看不到后续 Print

GAS 会在正式激活能力前检查 Cost 和 Cooldown。资源不足时，能力可能根本不会进入正常的 `ActivateAbility` 执行链，因此放在能力内部的 Print String 也不会执行。

可以这样理解：

```text
输入 ≠ 能力一定激活

输入
  → CanActivateAbility
     ├─ Cost 是否足够？
     ├─ 是否仍在 Cooldown？
     └─ 其他 Blocked/Required Tag 是否满足？
  → 全部通过后才真正激活
```

所以“没有生成投射物、也没有打印”并不一定是输入失效，可能是 GAS 在激活前拒绝了能力。

### 2.4 按技能等级缩放消耗

Cost GE 的 Magnitude 可以使用 Scalable Float 和 CurveTable：

```text
CT_Cost
└─ Fire.FireBolt
   Level 1 → 20
   Level 2 → 25
   Level 3 → 35
   Level 4 → 50
   ...
```

因为消耗是负数，可在 Scalable Float 中选择曲线并使用 `-1` 系数。`ApplyCost` 会用当前 Ability Level 应用 Cost GE，因此曲线的横轴就是技能等级。

注意区分：

- AbilitySpec 的 Level 决定本次技能等级；
- Cost GE 根据该 Level 查询曲线；
- AttributeSet 中的 Mana 是被修改的资源；
- UI 只是监听 Mana 变化并刷新进度条。

## 3. Cooldown：真正的技能冷却

### 3.1 Delay 为什么不是真正的冷却

原先在 FireBolt 中加入 Delay，只是让 Ability 晚一点结束。它存在几个问题：

- Delay 本身没有表达“角色拥有某个冷却状态”；
- UI 很难统一查询剩余时间；
- 不能自然参与 GAS 的 `CanActivateAbility` 判断；
- 多个技能无法复用统一的冷却规则；
- 网络预测和服务器权威语义不清晰。

冷却应当用带 Duration 的 GameplayEffect 表示，由它授予一个 Cooldown Tag。

### 3.2 新增原生冷却标签

本次提交增加：

```cpp
FGameplayTag Cooldown_Fire_FireBolt;
```

初始化：

```cpp
GameplayTags.Cooldown_Fire_FireBolt =
    UGameplayTagsManager::Get().AddNativeGameplayTag(
        FName("Cooldown.Fire.FireBolt"),
        FString("FireBolt Cooldown Tag"));
```

`Abilities.Fire.FireBolt` 表示能力身份，`Cooldown.Fire.FireBolt` 表示该能力当前处于冷却。二者不能互换。

### 3.3 创建 Cooldown GameplayEffect

创建：

```text
GE_Cooldown_FireBolt
```

配置重点：

```text
Duration Policy：Has Duration
Duration Magnitude：例如 0.5 / 3 / 5 秒
Granted Tags：Cooldown.Fire.FireBolt
```

再在 `GA_FireBolt` 的 Class Defaults 中设置：

```text
Cooldown Gameplay Effect Class：GE_Cooldown_FireBolt
Cooldown Tags：Cooldown.Fire.FireBolt（依具体版本配置）
```

提交技能后，Cooldown GE 应用到技能拥有者；在持续时间内 ASC 持有冷却标签，GAS 的激活检查会阻止 FireBolt 再次激活。GE 到期后标签被移除，能力重新可用。

### 3.4 冷却的权威来源

```text
权威：ASC 上的 ActiveGameplayEffect 与 CooldownTag
表现：技能球上的灰暗颜色和倒计时文本
```

即使 UI 倒计时因为帧率或定时器误差提前显示为 0，能否释放仍由 GAS 决定。不要反过来用 Widget 的变量阻止施法。

<a id="section-4"></a>
## 4. Ability 结束时机与多人投射物 Bug

### 4.1 Bug 表现

单人运行正常，但双人 PIE 中客户端施法时没有生成投射物。

### 4.2 原因

移除旧 Delay 后，蓝图在生成投射物节点后立即调用 `EndAbility`。客户端预测能力很快结束，相关任务或 RPC 流程可能在服务器完成投射物生成前被终止。

```text
客户端预测 ActivateAbility
  → 过早 EndAbility
  → 能力任务结束 / 状态清理
  → 服务器权威生成流程尚未走完
  → 客户端观察不到预期投射物
```

### 4.3 修复

不要在 Spawn Projectile 后立刻结束技能，把 `EndAbility` 接到 Montage Task 的结束出口：

```text
PlayMontageAndWait
├─ Completed ─┐
├─ Blend Out ─┼→ EndAbility
├─ Interrupted┤
└─ Cancelled ─┘
```

这样技能生命周期覆盖完整动画和发射流程，也给网络交互留出足够时间。

如果希望 Ability 结束后 Montage 仍播放，可根据设计取消 `Stop when Ability Ends`。但要理解其影响：能力已经结束时，Montage 仍可能继续；再次施法可能重新开始动画。

<a id="section-5"></a>
## 5. 为什么需要蓝图异步节点

技能球需要知道两件事：

- 冷却何时开始，以及初始剩余时间；
- 冷却何时结束。

不推荐在 Widget Tick 中每帧查询 ASC：

```text
每个技能球 × 每帧 × 查询 ActiveGameplayEffects
```

技能槽变多后会产生大量重复查询，而且 Widget 必须理解复杂 GAS API。本章创建一个事件驱动的代理：

```text
UWaitCooldownChange
├─ 监听 ASC 的 GameplayTag 变化
├─ 监听新 ActiveGameplayEffect
├─ 查询一次冷却总剩余时间
└─ 向蓝图广播 CooldownStart / CooldownEnd
```

它继承 `UBlueprintAsyncActionBase`，可在普通蓝图事件图中使用；`UAbilityTask` 则依附某个 GameplayAbility，主要供 Ability 内部使用。SpellGlobe 不是 Ability，所以这里选择通用 Blueprint Async Action。

<a id="section-6"></a>
## 6. `UWaitCooldownChange` 源码结构

### 6.1 委托就是异步节点的执行引脚

```cpp
DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(
    FCooldownChangeSignature,
    float,
    TimeRemaining);

UPROPERTY(BlueprintAssignable)
FCooldownChangeSignature CooldownStart;

UPROPERTY(BlueprintAssignable)
FCooldownChangeSignature CooldownEnd;
```

动态多播委托暴露到蓝图后，会成为异步节点右侧的执行分支和数据输出。广播 `CooldownStart(3.f)` 时，蓝图对应引脚被触发并得到 `TimeRemaining = 3`。

### 6.2 类声明与异步代理输出

```cpp
UCLASS(BlueprintType, meta=(ExposedAsyncProxy="ASyncTask"))
class AURA_API UWaitCooldownChange
    : public UBlueprintAsyncActionBase
```

`ExposedAsyncProxy` 让节点额外暴露任务对象引用。蓝图可以把它保存为 `CooldownChangeTask`，之后调用 `EndTask()`，避免创建新监听器时丢失旧任务。

### 6.3 静态工厂函数

```cpp
UFUNCTION(BlueprintCallable,
    meta=(BlueprintInternalUseOnly="true"))
static UWaitCooldownChange* WaitForCooldownChange(
    UAbilitySystemComponent* AbilitySystemComponent,
    const FGameplayTag& InCooldownTag);
```

蓝图异步节点通常由静态工厂函数创建对象并注册监听：

```cpp
UWaitCooldownChange* Task = NewObject<UWaitCooldownChange>();
Task->ASC = AbilitySystemComponent;
Task->CooldownTag = InCooldownTag;
```

`BlueprintInternalUseOnly` 表示它主要用于生成异步节点样式，而不是作为普通函数节点使用。

### 6.4 参数有效性检查

```cpp
if (!IsValid(AbilitySystemComponent) || !InCooldownTag.IsValid())
{
    Task->EndTask();
    return nullptr;
}
```

ASC 或 Tag 无效时无法监听。蓝图调用前同样应确保 WidgetController 已设置、AbilityInfo 已经广播，并且当前技能确实配置了 CooldownTag。

<a id="section-7"></a>
## 7. 同时监听“开始”和“结束”

### 7.1 冷却开始：监听 Active GE 被添加

```cpp
ASC->OnActiveGameplayEffectAddedDelegateToSelf.AddUObject(
    Task,
    &UWaitCooldownChange::OnActiveEffectAdded);
```

冷却开始本质上是一个 Duration GameplayEffect 被应用。因此监听 Active GE Added，可以获得 `FGameplayEffectSpec` 并检查它是否包含目标冷却标签。

```cpp
FGameplayTagContainer AssetTags;
SpecApplied.GetAllAssetTags(AssetTags);

FGameplayTagContainer GrantedTags;
SpecApplied.GetAllGrantedTags(GrantedTags);

if (AssetTags.HasTagExact(CooldownTag) ||
    GrantedTags.HasTagExact(CooldownTag))
{
    // 查询剩余时间并广播开始
}
```

检查两类标签增强了兼容性：冷却标识可能作为 AssetTag，也可能作为 GrantedTag 配在 GE 中。

### 7.2 查询剩余时间

```cpp
FGameplayEffectQuery Query =
    FGameplayEffectQuery::MakeQuery_MatchAnyOwningTags(
        CooldownTag.GetSingleTagContainer());

TArray<float> TimesRemaining =
    ASC->GetActiveEffectsTimeRemaining(Query);
```

为什么返回数组？因为同一个标签理论上可能由多个 Active GE 提供。提交中的处理取最大值：

```cpp
float TimeRemaining = TimesRemaining[0];
for (float Time : TimesRemaining)
{
    TimeRemaining = FMath::Max(TimeRemaining, Time);
}
CooldownStart.Broadcast(TimeRemaining);
```

选择最大剩余时间意味着：只要任一匹配冷却仍有效，UI 就显示最长的限制时间，更接近“何时真正恢复可用”。

### 7.3 冷却结束：监听 Tag Count

```cpp
ASC->RegisterGameplayTagEvent(
    InCooldownTag,
    EGameplayTagEventType::NewOrRemoved)
    .AddUObject(Task, &UWaitCooldownChange::CooldownTagChange);
```

回调收到 `NewCount`：

```cpp
if (NewCount == 0)
{
    CooldownEnd.Broadcast(0.f);
}
```

这里使用数量而不是简单的 bool 很重要：多个 GE 都授予同一标签时，某一个移除不代表冷却结束；只有标签聚合计数降到 0，角色才完全不再拥有该 CooldownTag。

<a id="section-8"></a>
## 8. `EndTask` 与生命周期管理

提交中的实现：

```cpp
void UWaitCooldownChange::EndTask()
{
    if (!IsValid(ASC)) return;

    ASC->RegisterGameplayTagEvent(
        CooldownTag,
        EGameplayTagEventType::NewOrRemoved)
        .RemoveAll(this);

    SetReadyToDestroy();
    MarkAsGarbage();
}
```

作用：

1. 从 GameplayTag Event 中解绑当前任务；
2. 告诉异步系统对象可以销毁；
3. 避免旧 Task 持续监听、重复广播或造成对象无法回收。

蓝图中推荐顺序：

```text
IsValid(CooldownChangeTask)
  → True：EndTask
  → WaitForCooldownChange(ASC, CooldownTag)
  → 保存新的 AsyncTask 引用
```

### 8.1 当前提交值得注意的清理点

`EndTask` 移除了 GameplayTag 事件，但源码还通过以下委托监听 Active GE：

```cpp
ASC->OnActiveGameplayEffectAddedDelegateToSelf.AddUObject(...)
```

更完整的清理通常也应执行：

```cpp
ASC->OnActiveGameplayEffectAddedDelegateToSelf.RemoveAll(this);
```

否则旧对象在销毁前仍可能留在委托调用列表中。`AddUObject` 对 UObject 生命周期有一定安全处理，但主动成对解绑更清晰，也能避免重复监听。后续重构时应优先补上这一点。

## 9. AbilityInfo 增加 CooldownTag

本次提交扩展结构体：

```cpp
UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
FGameplayTag CooldownTag = FGameplayTag();
```

现在 `FAuraAbilityInfo` 的职责变为：

| 字段 | 来源 | 用途 |
|---|---|---|
| AbilityTag | Ability 类 | 标识是什么技能 |
| InputTag | AbilitySpec 运行时动态标签 | 标识当前在哪个技能槽 |
| CooldownTag | AbilityInfo DataAsset | 告诉 UI 要监听哪个冷却状态 |
| Icon | AbilityInfo DataAsset | 技能图标 |
| BackgroundMaterial | AbilityInfo DataAsset | 技能球背景 |

在 `DA_AbilityInfo` 的 FireBolt 条目中设置：

```text
AbilityTag：Abilities.Fire.FireBolt
CooldownTag：Cooldown.Fire.FireBolt
Icon：FireBolt 图标
BackgroundMaterial：火焰技能背景材质
```

OverlayWidgetController 广播整个 Info，匹配 InputTag 的 Globe 保存 `CooldownTag`，随后才创建监听任务。

<a id="section-10"></a>
## 10. SpellGlobe 蓝图操作流程

### 10.1 初始化顺序

正确顺序是：

```text
WidgetControllerSet
  → 绑定 AbilityInfoDelegate
  → 接收 FAuraAbilityInfo
  → 判断 Info.InputTag == Self.InputTag
  → 设置 Icon / Background
  → 保存 Info.CooldownTag
  → 结束旧 CooldownChangeTask（若存在）
  → WaitForCooldownChange(ASC, CooldownTag)
  → 保存新 Task 引用
```

不能刚绑定 AbilityInfoDelegate 就立刻启动任务，因为此时 Globe 还没有收到与自身匹配的能力信息，`CooldownTag` 可能仍为空。

### 10.2 `CooldownStart` 分支

```text
CooldownStart(TimeRemaining)
  → 保存 RemainingTime
  → SetCooldownState
     ├─ Background Tint 降低（例如 0.05）
     └─ CooldownText RenderOpacity = 1
  → SetTimerByEvent(UpdateCooldownTimer, TimerFrequency, Looping=true)
  → 保存 TimerHandle
```

技能球变暗能向玩家解释“有法力但仍不能释放”的原因。

### 10.3 使用 Timer 而不是 Tick

例如 `TimerFrequency = 0.1`：

```text
每 0.1 秒：
RemainingTime = RemainingTime - TimerFrequency
显示 Clamp(RemainingTime, 0, 初始时间)
```

UI 文本不需要每帧更新。10 Hz 的更新频率已经足够平滑，而且只在技能处于冷却时运行。

`Set Timer by Event` 必须勾选 Looping，否则只执行一次，倒计时不会继续。这正是本章调试时遇到的节点问题。

### 10.4 更新文本

```text
RemainingTime
  → Clamp（避免负值）
  → ToText(float)
     最小小数位数：1
     最大小数位数：1
  → Text_Cooldown.SetText
```

保留一位小数可稳定显示 `3.0、2.9……0.0`，不会因为整数位变化导致视觉格式跳动。

### 10.5 冷却结束

可以由两层信号收尾：

- UI 本地 RemainingTime 小于等于 0；
- 异步 Task 收到权威 CooldownTag Count 为 0。

结束处理：

```text
Clear and Invalidate Timer by Handle
→ SetDefaultState
   ├─ Background Tint = 1
   └─ CooldownText RenderOpacity = 0
```

推荐把权威 `CooldownEnd` 也连接到清理逻辑，以修正本地定时器累计误差。再次强调：Timer 是显示用近似倒计时，Tag 移除才是 GAS 冷却真正结束。

## 11. 常见 Bug 与排查

### 11.1 扣蓝但没有冷却

- `GA_FireBolt` 是否调用了 `CommitAbility`；
- 是否配置 Cooldown GE Class；
- Cooldown GE 是否为 Has Duration；
- GE 是否授予正确的 `Cooldown.Fire.FireBolt`；
- Ability 的冷却标签是否与 GE 一致。

### 11.2 冷却生效但 UI 不变暗

- `DA_AbilityInfo` 是否配置 CooldownTag；
- Globe 是否先匹配 InputTag 后才保存 CooldownTag；
- 是否成功取得 ASC；
- `WaitForCooldownChange` 输入 Tag 是否有效；
- `CooldownStart` 是否广播；
- 技能球是否保存了异步任务引用。

### 11.3 倒计时只更新一次

`SetTimerByEvent` 没有启用 Looping，或 TimerHandle 被立即清除。

### 11.4 倒计时出现负数

本地递减会受浮点误差影响。显示前 Clamp 到 0，并在 `<= 0` 时清除 Timer。

### 11.5 多次换技能后一次冷却触发多个回调

旧的 AsyncTask 没有 `EndTask`，或 ActiveGameplayEffectAdded 委托没有解绑。创建新 Task 前结束旧 Task，并确保所有已注册委托成对移除。

### 11.6 客户端没有投射物

Ability 在客户端预测流程中过早 EndAbility。把结束节点接到 Montage Task 的 Completed / BlendOut / Interrupted / Cancelled，而不是生成投射物后立即结束。

### 11.7 法力不足仍显示可用

当前灰暗效果只代表冷却，没有表示 Cost 不足。后续可监听 Mana 变化，并根据 `CheckCost` 或计算出的 Ability Cost 给技能球增加“资源不足”状态；不要把它与 Cooldown 状态混为一谈。

## 12. 第 21.14 节：建模模式补洞工作流

本节与冷却系统相对独立，主要解决模块化地牢网格之间存在约半米缝隙、角色能穿过去的问题。

### 12.1 拼装与合并

```text
开启移动吸附（例如 100 uu）
→ 使用 1×1、1×2、2×3、3×3 模块拼出目标体积
→ 全选构成大块的 StaticMeshActor
→ Shift+5 进入 Modeling Mode
→ Create / Merge
→ 命名新静态网格
→ Accept
```

合并后把资产移回统一的 Dungeon 目录，不要长期留在 Map 自动生成目录中。

### 12.2 重建碰撞

合并网格可能继承许多复杂碰撞块。对于规则墙体：

```text
Static Mesh Editor
→ Remove Collision
→ Add Simplified Box Collision
→ 检查 Player、Projectile、Visibility 通道
```

简单盒碰撞更稳定，也通常比大量三角形碰撞更便宜。

### 12.3 遮挡渐隐

合并网格使用多个 Material Slot 时，每个 Slot 都需要对应的渐隐材质实例。把新网格放入 Fade Actor 后测试：

- 角色路径是否完全阻塞；
- Visibility Trace 是否被正确阻挡；
- 镜头遮挡时是否渐隐；
- 投射物通道行为是否符合预期。

## 13. 完整测试清单

### Cost

- FireBolt 每次成功施放都扣除正确 Mana；
- Mana 不足时能力不激活；
- 不会出现 Mana 被扣两次；
- Ability Level 改变时 Cost 按曲线变化；
- 服务器和客户端看到的 Mana 最终一致。

### Cooldown

- 施法后 ASC 获得正确 CooldownTag；
- 冷却期间连续点击不会再次激活；
- 冷却到期后 Tag Count 归零；
- 多个同标签 GE 存在时，以最长剩余时间显示；
- `CommitAbility` 失败时不错误应用 Cost 或 Cooldown。

### UI

- 只有对应 InputTag 的 Globe 监听该冷却；
- 冷却开始图标变暗、文本出现；
- 倒计时持续更新且不显示负数；
- 冷却结束恢复亮度、隐藏文本、清除 Timer；
- Widget 重建或技能换槽时旧 AsyncTask 被结束；
- Listen Server 与远程 Client 都有正确反馈。

### 多人 Ability 生命周期

- 客户端施法能看到服务器权威投射物；
- Ability 不在发射节点后过早结束；
- Montage 的四个结束出口均能清理 Ability；
- 冷却和 Cost 以服务器结果为准；
- UI 定时器误差不会改变实际可施法判断。

<a id="section-14"></a>
## 14. 本章最重要的理解

### 14.1 Cost 和 Cooldown 都是 GameplayEffect

Cost 用 Instant GE 修改资源；Cooldown 用 Duration GE 在一段时间内授予标签。`CommitAbility` 把二者纳入标准 GAS 激活流程，因此不需要在每个技能蓝图中手写“Mana -= 20”和“CanCast = false”。

### 14.2 Tag 是状态协议

`Cooldown.Fire.FireBolt` 不只是一个名称。它是 Ability、GameplayEffect、ASC 查询和 UI 监听共同遵守的协议：GE 授予它，GAS 用它阻止激活，异步 Task 用它过滤事件，SpellGlobe 用它选择要显示的冷却。

### 14.3 异步节点是 GAS 到蓝图 UI 的适配器

`UWaitCooldownChange` 把复杂的 ASC 委托、EffectQuery 和 Tag Count 封装成两个简单输出：开始与结束。Widget 不需要每帧查询 GAS，也不需要知道 ActiveGameplayEffect 的内部结构。

### 14.4 表现不等于权威状态

技能球上的数字是本地显示；ASC 的 Active GE 和 GameplayTag 才决定能力是否能激活。良好的网络游戏架构应始终让服务器/GAS 维护规则，让客户端 UI 对权威状态做及时、平滑的反馈。

完成本章后，项目已经有了一套可推广到所有技能的模板：每个技能配置 AbilityTag、InputTag、Cost GE、Cooldown GE 和 CooldownTag；通用异步任务负责监听，通用 SpellGlobe 负责显示。后续增加新技能时主要是添加数据，而不是复制整套逻辑。
