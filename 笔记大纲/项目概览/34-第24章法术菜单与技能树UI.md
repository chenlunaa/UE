## 1. 法术菜单的设计目标

法术菜单需要同时支持：

- 显示攻击和被动能力树；
- 区分锁定、可解锁和已解锁状态；
- 选择技能并显示描述；
- 使用法术点解锁或提升能力；
- 将已装备能力显示在底部装备行；
- 为后续装备到输入槽、多人同步和技能等级扩展预留接口。

它比简单的“技能列表”复杂，但仍保持组件化，避免把所有节点堆在一个巨大 Widget 中。

---

<a id="section-2"></a>
## 2. 菜单由哪些区域组成

```text
WBP_SpellMenu
├─ Header：法术点、标题、关闭按钮
├─ TreeSide
│  ├─ WBP_OffensiveSpellTree
│  └─ WBP_PassiveSpellTree
├─ DescriptionSide
│  ├─ 分隔线
│  ├─ Ability Name
│  ├─ Ability Description
│  └─ Spend Point / Equip 按钮
└─ EquippedSpellRow
   └─ 多个 WBP_SpellGlobeButton
```

攻击树和被动树各自负责内部布局，主菜单只负责摆放区域和协调选择结果。

---

<a id="section-3"></a>
## 3. 可交互的法术球基类

Overlay 中的 `WBP_SpellGlobe` 主要用于显示技能状态，不一定适合点击。法术菜单需要一个真正的 Button，因此创建独立的可交互基类：

```text
WBP_SpellGlobeButton
├─ Button
├─ Background Image
├─ Icon Image
├─ Lock Image
└─ Selected Image
```

状态含义：

| 状态 | 表现 |
|---|---|
| Locked | 显示锁图标，不能正常选择 |
| Unlocked | 显示技能图标，可选中 |
| Selected | 额外显示选中圈或高亮动画 |
| Equipped | 在装备行中显示已装备状态 |

锁定背景、图标、选中圈和玻璃效果通过材质实例控制。选中图层默认透明，点击后再把 Render Opacity 调高，避免改变按钮本体布局。

<a id="section-4"></a>
## 4. 攻击和被动技能树

### 4.1 攻击技能树

攻击树采用三列布局，每列包含三个技能球，列之间使用 Spacer 控制间距；技能球之间用 Image 作为连接线。

```text
OffensiveSpellTree
├─ Column 1：3 个按钮
├─ Spacer
├─ Column 2：3 个按钮
├─ Spacer
└─ Column 3：3 个按钮
```

每个技能按钮都是独立 Widget，后续可替换图标、背景、锁定状态和选中动画，而不改变树的布局。

### 4.2 被动技能树

被动树复用攻击树的结构和样式，但使用独立材质实例调整暗度、边缘阴影和噪声速度。不要直接修改共享材质，否则会同时改变 Overlay 技能球和攻击树的外观。

---

<a id="section-5"></a>
## 5. 装备技能行

底部装备行不是技能树，而是当前已装备技能的槽位集合：

```text
EquippedSpellRow
├─ Passive Slot 1
├─ Passive Slot 2
├─ Passive Slot 3
└─ Offensive / Active Slots
```

它复用可交互球体的视觉，但布局重点是水平排列、固定宽度和不换行。使用 WrapBox 时要留意自动换行；必要时将路由改为水平填充，或使用 HorizontalBox 保证槽位固定排列。

本章只完成静态槽位的构图，装备按钮点击后的能力分配尚未接入 ASC。

---

<a id="section-6"></a>
## 6. 法术菜单主 Widget

法术菜单复用属性菜单的总体布局思路：左侧树、右侧描述、顶部资源、底部装备行。复制基础 Widget 后需要清理属性菜单专属内容：

- 属性行和属性点区域；
- 不属于法术菜单的按钮绑定；
- 旧的关闭事件分散逻辑。

推荐保留统一的根布局和关闭按钮，使两个菜单在 HUD 中拥有一致的尺寸、边距和动画体验。

<a id="section-7"></a>
## 7. 描述面板与视觉材质

选择技能后，右侧描述面板应填充：

```text
Ability Name
Ability Description
当前等级 / 解锁需求
Spend Point
Equip
```

描述区域使用 Spacer、Text 和 Button 组合，并通过材质实例统一滚动纹理、云层、边缘阴影和颜色。材质参数调整应优先修改菜单专用 MI，避免全局材质联动造成 UI 风格漂移。

布局调试时同时检查：

- 锚点是否一致；
- Alignment 是否导致位置偏移；
- 图片与相框宽度是否相同；
- 菜单打开后是否覆盖等级球或肖像框。

---

<a id="section-8"></a>
## 8. 菜单打开、关闭与生命周期

属性菜单和法术菜单都应通过统一的关闭委托通知 Overlay：

```text
Close Button OnClicked
  → Remove From Parent
  → MenuClosed.Broadcast
  → Overlay 清理引用和输入模式
```

将关闭流程收拢成 `CloseMenu` 函数，避免点击关闭、Widget 销毁和其他路径各自重复处理 Overlay 状态。

菜单创建时由外部设置 WidgetController；菜单自身只订阅需要的委托，不要在设计器预览阶段假定 ASC、PlayerState 一定有效。

---

<a id="section-9"></a>
## 9. WidgetController 的依赖重构

随着法术菜单出现，Controller 不应让每个子 Widget 都直接依赖 `AuraAbilitySystemComponent`。重构方向是让基类集中持有四个核心对象：

```text
PlayerController
PlayerState
AbilitySystemComponent
AttributeSet
```

并通过统一 Getter 提供：

```text
GetAuraPC()
GetAuraPS()
GetAuraASC()
GetAuraAS()
```

子类（Overlay、AttributeMenu、SpellMenu）只使用自己需要的对象。这样可以减少重复 Cast、避免 WidgetController 之间的初始化差异，也便于未来加入 AbilityMenu 专属数据。

重构后应删除已经冗余的启动能力广播或重复初始化代码，并全量编译检查其他 Controller 是否仍依赖旧接口。

<a id="section-10"></a>
## 10. 当前功能边界与后续路线

本章主要是法术菜单 UI 和通信骨架，以下功能还没有完成：

1. 根据 AbilityInfo 自动填充所有技能图标；
2. 根据玩家等级和法术点判断技能是否可解锁；
3. 消耗 SpellPoints 解锁或升级能力；
4. 将技能装备到具体 InputTag 槽位；
5. 多人环境下同步解锁、等级和装备状态；
6. 选择技能后刷新描述面板的完整数据。

后续实现应继续遵循：

```text
服务器保存能力状态
  → ASC / AbilitySpec 提供运行时信息
  → WidgetController 合并静态 AbilityInfo
  → SpellButton 只显示状态并发送用户意图
```

<a id="section-11"></a>
## 11. 测试清单

- [ ] 攻击树三列布局在不同分辨率下不重叠；
- [ ] 被动树与攻击树间距和宽度一致；
- [ ] 锁定、解锁、选中状态显示正确；
- [ ] 选中圈默认隐藏，点击后正确显示；
- [ ] 装备行不发生意外换行；
- [ ] 描述面板在选择技能后能填充；
- [ ] 法术菜单关闭后从父级移除；
- [ ] 重复打开和关闭不会叠加多个菜单实例；
- [ ] Overlay、AttributeMenu、SpellMenu 均能获得正确 Controller；
- [ ] Controller 重构后项目完整编译通过；
- [ ] 菜单不会遮挡等级球、肖像框等已有 HUD；
- [ ] Standalone 与多人 PIE 下初始化顺序一致。

<a id="section-12"></a>
## 12. 本章核心认识

法术菜单的难点不是摆放几个图片，而是把“能力树、能力状态、资源消耗、装备槽位和网络状态”拆成可替换组件。当前章节先完成视觉和通信边界，后续再把 GAS 的 AbilitySpec、SpellPoints 和 InputTag 接入这些按钮。
